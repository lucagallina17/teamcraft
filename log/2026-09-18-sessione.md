# Sessione 2026-09-18 — Deploy backend TeamCraft su Azure

## Obiettivo della sessione
Primo deploy end-to-end del backend TeamCraft.API su Azure App Service, collegato ad Azure SQL Database (Resource Group, SQL Server e DB già creati da Luca prima della sessione).

## Cosa è stato implementato/modificato

- **Scoperto e corretto un mismatch iniziale**: la cartella `src/` risultava vuota a inizio sessione; il codice reale è stato individuato in `src/backend/TeamCraft/` (backend) e `src/frontend/teamcraft-fe/` (frontend) dopo che Luca l'ha spostato lì. Esiste anche una cartella residua `TeamCraft.API/` (scaffold iniziale, non referenziata dalla `.sln`) da pulire in futuro — il progetto realmente in uso è `TeamCraft/TeamCraft.API.csproj`.
- **Migrazione .NET 7 → .NET 8** su tutti e 5 i progetti (`Domain`, `Application`, `Infrastructure`, `API`, `Tests`): TargetFramework aggiornato, EF Core 7.0.20 → 8.0.31, `Microsoft.AspNetCore.OpenApi` → 8.0.31. Build e 9/9 test verificati dopo l'upgrade.
- **`Program.cs`**:
  - Aggiunto `db.Database.Migrate()` all'avvio (auto-migrate).
  - CORS: origin letti da configurazione (`Cors:AllowedOrigins` in `appsettings.json`, default `http://localhost:4200`) invece di hardcoded.
  - Swagger abilitato anche in ambiente Production (non solo Development).
- **Downgrade MassTransit 9.2.0 → 8.5.10** (`Application.csproj`, `Tests.csproj`): la 9.x richiede una licenza a pagamento anche per l'In-Memory Transport.
- **CLAUDE.md** e questo `MEMORY.md` aggiornati per riflettere lo stack .NET 8.
- Installato **Azure CLI** (winget) sulla macchina locale.
- **Visual Studio aggiornato** da 17.6.33723 a 17.14.41 (necessario per supportare .NET 8 come target — vedi problemi risolti).

## Decisioni architetturali prese e perché

1. **.NET 8 invece di .NET 10**: scelto per minor attrito (SDK 8 già installato in locale, poche breaking change da .NET 7). Trade-off esplicitato: .NET 8 LTS termina il supporto a novembre 2026, quindi tra circa 2 mesi andrà rivalutato un ulteriore upgrade (probabilmente a .NET 10, già LTS corrente).
2. **Auto-migrate EF Core all'avvio** (`Database.Migrate()` in `Program.cs`) invece di migration manuali da locale: accettabile per un App Service a singola istanza (tier F1); da rivedere se in futuro si scala a più istanze (rischio di corse tra istanze).
3. **Deploy scope limitato al solo backend** in questa sessione; il frontend Angular resta da deployare in una sessione successiva (probabilmente su Azure Static Web Apps).
4. **Swagger abilitato anche in Production**: scelta consapevole per un progetto portfolio dimostrabile — nessun dato sensibile esposto tramite lo schema API.

## Problemi risolti (in ordine cronologico)

1. **.NET 7 non più selezionabile su Azure Portal** (EOL da maggio 2024) → upgrade a .NET 8 (vedi sopra).
2. **Visual Studio non compilava progetti net8.0** (`NETSDK1045`) nonostante l'SDK 8.0.414 fosse installato a livello di sistema: VS usa un proprio toolset MSBuild interno legato alla versione dell'IDE, non gli SDK esterni. Risolto aggiornando VS a 17.14.41 (supporto .NET 8 richiede VS ≥ 17.8).
3. **Deploy via Kudu "Zip Push Deploy" (drag&drop nel browser) sistematicamente fallito**: un componente chiamato `QuickDeployBuilder`, introdotto in questa versione 2026 del tooling Azure, forza sempre `Perform Server Side Build: True` e tenta di ricompilare lo zip con Oryx come se fosse codice sorgente, fallendo con `Couldn't detect a version for the platform 'dotnet'` — **ignora completamente** le app settings `SCM_DO_BUILD_DURING_DEPLOYMENT=false` e `WEBSITE_RUN_FROM_PACKAGE=1` che dovrebbero disattivarlo. Conclusione: questo specifico strumento GUI è **inutilizzabile** per deploy di binari .NET già compilati in questo ambiente. Bypassato passando al Publish di Visual Studio.
4. **`az login` con broker nativo Windows falliva** (`TypeError: argument of type 'NoneType' is not a container or iterable`, bug del broker WAM in questo ambiente) → risolto con `az login --use-device-code`. Serviva inoltre `--tenant <id>` esplicito per soddisfare correttamente una policy di Conditional Access con MFA obbligatoria. **Non risolto del tutto**: dopo login e MFA riusciti, CLI segnalava "No subscriptions found" per l'account usato — non è stato chiarito se fosse un problema di account sbagliato o di permessi; il percorso CLI è stato abbandonato a favore di Visual Studio Publish, quindi resta un'indagine aperta se si vorrà usare `az` in futuro.
5. **`WEBSITE_RUN_FROM_PACKAGE=1`** (impostato come workaround per il tentativo Kudu, poi abbandonato) è rimasto attivo e confliggeva col meccanismo di deploy di Visual Studio → `/home/site/wwwroot` risultava vuoto (`The application 'TeamCraft.API.dll' does not exist`). Risolto rimuovendo l'app setting.
6. **MassTransit 9.2.0 richiede licenza a pagamento**: anche solo configurando l'In-Memory Transport, l'app andava in crash all'avvio (`MassTransit.ConfigurationException: License must be specified`). Risolto con downgrade a 8.5.10 (ultima major open-source), nessuna modifica al codice necessaria.

## Esito finale

Deploy completato con successo:
- App Service (Linux, F1, .NET 8) raggiungibile su `https://teamcraft-api-g5bfaecpdjevf3cf.westeurope-01.azurewebsites.net`
