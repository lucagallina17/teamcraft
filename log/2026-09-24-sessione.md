### Deploy Azure
- Backend ripubblicato da Visual Studio con tutto il lavoro sopra.
- Primo deploy: **500 su ogni richiesta, anche pubbliche** (es. `/api/auth/login`). Causa: `Jwt:Key` vive solo nei User Secrets locali (mai committato), mai aggiunto alle App Settings di Azure → `UseAuthentication` va in eccezione non gestita su ogni richiesta, prima ancora di controllare permessi. Risolto aggiungendo `Jwt__Key` alle Environment variables + **restart esplicito** da Overview (il salvataggio da solo non bastava).
- Scoperto un problema di bootstrap: con `[Authorize]` su `EmployeesController`, non si può più creare il primo `Employee` via API senza essere già autenticati — ma non ci si può autenticare senza un `Employee` esistente con la propria email. Soluzione in corso: inserire il primo `Employee` a mano via Query editor SQL del Portale (l'endpoint di registrazione resta pubblico apposta, quindi da lì in poi il flusso normale funziona). Il Query editor ha richiesto di whitelistare l'IP di Luca sul firewall del SQL Server (pulsante diretto nel Portale).

## Decisioni prese e perché

1. **`[Authorize]` per-action, non per-classe**: scelta di Luca. Funziona identico, ma segnalato il rischio: una nuova action futura in quei controller resta pubblica di default se ci si dimentica l'attributo (con l'approccio per-classe il default sarebbe stato "protetto").
2. **`CreatedBy` letto dal claim del token invece che dal client**: stessa famiglia di problema già affrontata ieri (ruolo auto-assegnato, dipendente scelto a caso) — un client non deve mai poter decidere un dato di identità/attribuzione che il server può ricavare da sé.
3. **Bootstrap del primo utente via inserimento SQL diretto**, non un endpoint speciale "crea il primo admin": più semplice, non introduce un varco permanente nell'API, un'operazione una tantum.
4. **Visualizzazione recensione con stelle disegnate a mano invece di `p-rating` in sola lettura**: `p-rating` non ha un input `value` bindabile (solo `formControlName`), quindi creare un form fittizio solo per mostrare un valore sarebbe stata complessità ingiustificata.

## Problemi risolti

1. **Confusione iniziale sul perché servisse `[Authorize]`** nonostante la JWT fosse "già fatta": chiarito che autenticazione (chi sei) e autorizzazione (`[Authorize]`, puoi fare questo) sono due middleware distinti — il primo valida un token se c'è, il secondo decide se bloccare la richiesta, e senza il secondo il primo non serve a nulla.
2. **`TeamReviewAggregate` non raggiungibile**: vedi sezione implementazione sopra — mancavano il collegamento a MediatR, l'endpoint e l'implementazione del repository.
3. Bug minori trovati in revisione durante la scrittura guidata: query sul DbSet sbagliato (`_context.Teams` invece di quello delle recensioni), filtro su `Id` invece che su `TeamId`, `FirstOrDefault` invece di `FirstOrDefaultAsync`, mismatch di nullabilità tra interfaccia e implementazione, conversione mancante Aggregate→DTO, punto e virgola di troppo dopo un blocco di proprietà (`CS1597`).
4. **`p-rating` senza input `value`**: scoperto controllando i metadati compilati del componente (`ɵɵngDeclareComponent`), non fidandosi dei soli `.d.ts`.
5. **500 generalizzato su Azure per `Jwt:Key` mancante**: diagnosticato testando un endpoint pubblico (`/api/auth/login`) per escludere che fosse un problema di permessi — dato che falliva anche lui, la causa doveva essere a monte, nel middleware di autenticazione stesso.
6. **Firewall SQL per il Query editor**: serve whitelistare l'IP client separatamente da "Allow Azure services", il Portale lo offre come azione diretta.
