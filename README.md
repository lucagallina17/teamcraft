# TeamCraft

A talent-matching system that builds optimal project teams from employee skills and working affinities.

You describe a project as a set of roles, each with required competencies (weight, minimum level, *Required* or *Preferred*). TeamCraft searches the pool of available employees and proposes the three best team compositions, then manages the team lifecycle from proposal to closure and end-of-project reviews.

> Hosted on Azure free tiers: the first request after a period of inactivity can be slow while the App Service wakes up.

## Features

- **Employees** with competency assessments and pairwise affinity scores between colleagues
- **Competencies** catalog and **project roles** with per-project requirements
- **Projects** with a controlled lifecycle (a project can only be physically deleted while in *Draft*)
- **Team proposals**: ranked, alternative compositions generated by the matching algorithm
- **Teams** (*Proposed* → *Active* → *Closed*) with member management; activating a team activates its project
- **Team reviews** submitted at the end of a project
- **Authentication**: employees register with their own email (matched against an existing record) and sign in to use the app; every endpoint except login and registration requires a valid token, and the authenticated user's id is used to attribute the actions they take

## The matching algorithm

Assigning people to role slots is a constrained optimisation problem, and a greedy approach (best candidate per slot in order) does not guarantee a global optimum. This was found through a failing test, which is why the implementation uses **backtracking with pruning**:

- Each candidate is scored against a role requirement (competency weight, minimum level, Required/Preferred).
- A small **affinity bonus** (weighted 0.1x, deliberately minor) rewards teams whose members work well together. Affinities are preloaded in a single query so the search runs entirely in memory.
- Slots are visited **scarcest first** (fewest eligible candidates), which both avoids sacrificing a slot that has no alternative and prunes the search tree fastest.
- Branches that cannot beat the best solution found so far (using the best possible score of the remaining slots as an upper bound) are abandoned.
- The search prefers filling more slots, then the higher total score, with a hard cap on visited nodes as a safety net.
- Employees already in an *Active* team on another project are excluded up front.
- Three genuinely different proposals are produced by excluding the top contributor of each optimal solution before searching for the next one.

## Architecture

Clean Architecture with four projects and a strict dependency rule:

```
API ──► Application ──► Domain
Infrastructure ──► Application ──► Domain
```

| Project | Responsibility |
|---|---|
| `TeamCraft.Domain` | Entities, aggregates, enums, domain events and exceptions. Depends on nothing. |
| `TeamCraft.Application` | Use cases: services, MediatR commands/queries/handlers, DTOs, repository interfaces. |
| `TeamCraft.Infrastructure` | EF Core `DbContext`, entity configurations, migrations, repository implementations. |
| `TeamCraft.API` | ASP.NET Core controllers, DI composition root, CORS, Swagger. |
| `Tests` | xUnit tests with Moq. |

Key design decisions:

- **Partial DDD.** `TeamAggregate` and `TeamReviewAggregate` are real aggregate roots (private setters, business rules inside, constructors that guarantee a valid state, internal constructors for child entities). Other entities are still anemic.
- **Aggregates reference each other by Id only.** Cross-aggregate rules live in the command handler, never inside an aggregate.
- **CQRS.** Separate repositories for writes (`ITeamAggregateRepository`, works on the aggregate) and reads (`ITeamReadRepository`, projects straight to DTOs with `.Select()`).
- **Domain event vs integration event.** `TeamActivatedEvent` (MediatR, in-process, synchronous) decouples "activate the team" from "activate the project". `TeamActivatedIntegrationEvent` (MassTransit) is meant for external consumers; today it runs on the in-memory transport.
- **Deterministic tie-breaks** on any query that feeds a decision, rather than relying on database ordering.

## Running locally

**Prerequisites:** .NET 8 SDK, Node.js 22, a SQL Server instance.

**Backend**

1. Point `ConnectionStrings:DefaultConnection` in `src/backend/TeamCraft/TeamCraft/appsettings.json` at your SQL Server instance.
2. Run the `TeamCraft.API` project (Visual Studio, or `dotnet run` from `src/backend/TeamCraft/TeamCraft`). EF Core migrations are applied automatically at startup.
3. Swagger is served at `/swagger` (use the "Authorize" button to test protected endpoints with a bearer token).

**Frontend**

```bash
cd src/frontend/teamcraft-fe
npm install
npm start
```

The development build reads the API address from `src/environments/environment.development.ts`; update `apiUrl` there if your API runs on a different port. Production builds use `src/environments/environment.ts`.

**Tests**

```bash
cd src/backend/TeamCraft
dotnet test
```

## Deployment

- **Frontend:** Azure Static Web Apps, built and published by a GitHub Actions workflow on every push to `main`. `staticwebapp.config.json` provides the SPA fallback for client-side routes.
- **Backend:** published to Azure App Service (Linux, .NET 8) from Visual Studio, connected to Azure SQL Database. The connection string, allowed CORS origins and JWT signing key are supplied as App Service environment variables (`ConnectionStrings__DefaultConnection`, `Cors__AllowedOrigins__0`, `Jwt__Key`), so no secrets live in the repository.
